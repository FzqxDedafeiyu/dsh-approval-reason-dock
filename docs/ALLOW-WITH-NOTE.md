# 需求：允许时带话（Allow with a note）

- 状态：**待排期**（2026-11-12 记录，尚未实现）
- 提出：主人（来自网友讨论）
- 目标版本：预计 `0.2.0`（新功能，minor）

## 1. 要解决的问题

现在插件只支持「拒绝时带理由」。但同意（允许一次）时也经常需要给模型补一句话：

- 「允许，但只改这个文件，别动别的」；
- 「这次允许是因为我在测试，下一步把 diff 发我」；
- 「可以用，但先 `--dry-run` 试一遍」；
- 「同意，注意别删目录」。

这些说明既不属于拒绝理由，也不该被丢掉。内置审批卡放行后没有任何附言通道，用户只能等下一轮再说 —— 常常已经晚了。

## 2. 用户可见行为（UX）

面板保留现有理由输入框，语义升级为「给模型的说明（可选）」：

- 输入框为空时：
  - 按钮 `允许一次`（原生行为，不发任何消息）与 `拒绝`（原生行为）；
- 输入框非空时：
  - 按钮变成 `允许并说明` 与 `拒绝并说明`；
  - 点任意一个：先把说明作为消息送进当前轮，再回答审批；
  - 点「允许并说明」→ 说明以「**（审批同意说明）**」前缀发出，然后 `answer('allowed-once')`；
  - 点「拒绝并说明」→ 保持现有行为，前缀「**（审批拒绝理由）**」，然后 `answer('rejected')`。
- 说明发送失败：**不回答审批**，保留面板 + 显示错误码，可重试或清空后重试（与拒绝路径一致，避免「说明丢了但工具已经执行」）。
- 成功放行后浮层立即收起；草稿按审批清理。
- 会话跟随、按审批草稿、折叠、会话名等既有行为不变。
- 子代理会话依旧完全不接管（DSH 自动拒绝提权，插件不渲染）。

示例（模型在下一轮看到的消息）：

```
（审批同意说明）只改 docs/ 下的文件，不要动 client.js。
```

## 3. 技术方案

仍是**纯客户端、零宿主**：复用现有 `remote.session.prompt` 通道。

- 发送顺序：先 `prompt({ mode: "steer" })` 投递说明 → 失败自动降级 `mode: "queue"` → 成功后再 `answer(outcome)`。
  - 注意与拒绝不同：允许的 outcome 是 `allowed-once`，需真机验证「审批挂起期间 steer 是否可用」以及「放行后工具执行顺序」，不可假设。
- 前缀新增一组 i18n：zh `（审批同意说明）` / en `(approval allow note) `（具体文案待定，需与 `prefix` 长度上限一起考虑）。
- 说明规范化沿用 `normalizeReason`：空白折叠、trim、长度上限。是否把允许的说明上限从 500 提到 1000 待定。
- 失败处理与拒绝一致：投递失败 → 不 answer，保留审批，显示错误。

## 5. 待验证的风险 / 未知点

1. **审批挂起期间 steer 是否可用**：拒绝路径已验证；允许路径需真机确认不会被运行时以「正在等待审批」拒绝。
2. **顺序语义**：说明先于 `answer('allowed-once')`，模型可能在工具执行前读到；若运行时把 queued 消息放到下一轮，语义是否可接受。
3. **失败策略**：说明投递失败时是否阻塞允许 —— 本设计选择阻塞（安全），需主人确认。
4. **长度上限**：允许说明是否与拒绝理由同为 500 字符，还是提高到 1000。
5. **按钮态**：两按钮动态文案 vs 四按钮常驻，选前者（界面更简洁），需真机看效果。
6. **与内置卡一致性**：允许后内置卡消失，浮层也要立刻消失；错误时内置卡仍在，浮层也应仍在。

## 6. 不做的事（保持非侵入定位）

- 不接管/替换内置审批卡；
- 不加宿主半、不挂 `tools/*` 钩子、不改 tool result（与 `dsh-why-reject-me` 的通道不同，我们的说明走普通 steering 用户消息，便于人类阅读）；
- 不为子代理会话提供带话（DSH 在子代理上下文自动拒绝提权）。
